# Engineer Quest 全流程开发文档 V1.1

版本 V1.1 · 2026 年 11 月 11 日 · 开发评审稿

本文件把 Engineer Quest 的课堂游戏流程落实为研发可以拆解的功能、数据和验收要求。面向零基础高中生，以同一个智能灯项目串联需求评审、虚拟接线、积木原型、轻代码、实物验证和选修拓展。当前交付是开发文档，不代表代码、硬件链路或教学时长已经验证。

# 1 文档关系与本轮变更

原始 PRD V1.0 保留为立项资料。本文件更新游戏主线与阶段职责，技术架构、安全约束和运营要求沿用原始 PRD，并在下面明确需复核的实现细节。同一问题发生冲突时，按本文件的新版流程进行产品评审；未解决的技术选项不能被当作已冻结规格。

本轮采用的流程：上课发手册和讲背景 → 网站注册员工身份 → 点击 NPC 领取任务 → 中文需求评审及输出方案 → 学习硬件和图形化接线 → 完成图形化 Demo → 轻代码实现 → 真机测试和教师验证 → 完成较快的小组进入商城拓展。

与 V1.0 的主要差异：

| 方面 | V1.1 开发要求 |
| --- | --- |
| 学习顺序 | 将中文需求评审前置，虚拟硬件认识和接线移到完整积木 Demo 之前 |
| 两次评审 | 第一次讨论要解决什么；第二次围绕硬件方案和原型证据讨论怎么实现，不重复答题 |
| 图形化工具 | 接线画布与积木编程是两个工具，共享同一项目、设备和版本 |
| NPC | 从通用帮助入口扩展为需求与方案评审角色；不承担实物安全批准 |
| 轻代码 | 先展示学生自己的方案，再以小需求变更驱动修改；不机械重抄积木 |
| 教师 | 节点跟进、走访教学、硬件安全与实物验收 |
| 排行榜 | 加入班级内员工成果展示；指标、个人或小组口径及隐私呈现仍需确认 |
| 拓展 | 商城属于完成基础交付后的选修，不影响基础结业 |

# 2 目标与首期范围

学生应能用中文解释输入、判断、输出和重复执行；看懂并修改一段控制灯的代码；参与接线、测试或排错；通过经历判断自己对需求、硬件、软件、测试工作的兴趣。

首期只做一个基础客户订单和少量审核过的拓展订单。主线对象是低压 LED 灯控演示装置，不是可接市电的照明产品。保留原创公司、客户、NPC、邮件、手册、工程币和工位的沉浸感，不复制《深圳 I/O》的素材、角色、文本或关卡。

不做通用 C++ 在线执行、完整电路物理仿真、任意硬件自由接入、真实货币支付、公开职业能力排名或 AI 自动判定职业适配。首期也不承诺任意代码可以无损转回积木。

# 5 首个客户订单

## 5.1 客户委托

客户希望做一个桌面演示装置：环境暗时自动点亮 LED，环境亮时关闭；能持续观察变化，不是只启动一次。基础材料由公司提供，先完成安全、可演示的版本。手动开关、显示屏和稳定性优化属于后续变更，不在第一轮需求里堆满。

故事中的客户关心“在什么情况下灯应该怎样工作”；具体传感器、引脚和语法在之后引出。避免先把完整代码交给学生，再让学生复述答案。

## 5.2 需求卡

保存以下字段：客户场景、输入信息、判断规则、输出动作、持续运行要求、明确不做的功能、学生选择理由、需求版本。

学生可以从中文选项开始，再补充一句自己的解释。允许不同合理表达；判断逻辑必须能映射为可测试的行为。示例是“如果环境暗，就开灯；否则关灯，并持续检查”，不要求第一关知道 analogRead 或 if 的拼写。

NPC 每轮只围绕一个具体问题：设备凭什么知道暗了？从暗变亮时会发生什么？只在开机判断一次够不够？模型提出的是教学问题，不把未经批准的新功能加入基础通关要求。

# 6 各阶段交互要求

## 6.1 S0 入职

教师创建场次并冻结课程与手册版本。学生用课堂邀请码和昵称加入，创建员工身份；不把真实姓名、手机号或学校作为主线必填项。再次进入应恢复原身份与进度，不能因刷新重复发初始奖励。

入职页先展示公司和客户，再给出“进入工位”和“找 NPC 接单”。背景介绍保持短，长资料放在手册中。必须展示低压实验与教师批准后上电的规则。

## 6.2 S1 需求评审

界面包含客户委托、NPC 对话、中文方案选项和右侧需求卡。学生选择或解释后，需求卡显示更新预览；提交才生成不可变版本。NPC 可以建议补充，不能悄悄改写学生最终选择。

基础覆盖项由固定规则检查，NPC 负责语义讨论。模型不确定时转为可选择的问题卡，不让学生无限对话。通过意味着方案已具备进入实验的条件，不意味着学生掌握了代码或真实硬件。

## 6.3 S2 工程准备与设计审核

引导顺序：认识开发板 → 电源与 GND → 输入与输出 → 灯及限流元件 → 传感器 → 信号与引脚映射。每个小步骤在纸质手册和电子手册有同一节编号。

虚拟接线画布支持拖元件、选端子、连线、撤销和保存。点击引脚显示中文用途及限制。基础规则至少覆盖缺地、错误信号口、LED 极性、缺少限流电阻、电源短接和程序与接线引脚不一致。

此阶段可由系统提供经过审核的最小点灯程序验证接线，但明确标记为引导实验，不记为学生独立完成完整逻辑。进入 S3 时保留接线和元件，开始由学生搭建自动灯逻辑。

## 6.4 S3 完整图形化 Demo

首期积木包括读取输入、变量、比较、如果否则、输出、重复执行和等待。不使用“一键做自动灯”的整题积木。

运行时显示当前执行分支、变量值和灯状态。测试反馈按“模拟输入、预期动作、实际动作、相关步骤”呈现。学生可手动调光，也可运行固定测试序列。

提交后 NPC 技术负责人结合真实积木、接线和测试记录讨论方案。一旦发现客观测试失败，先定位测试证据，不用模型的“我认为正确”覆盖失败结果。学生修改方案后重新提交版本和测试。

## 6.5 S4 轻代码

先并排展示积木与代码映射，再开放有限编辑区域。初始化、引脚声明等可以折叠，但必须可查看。学生完成一个小变更，例如调整何时开灯，或在进阶关加入手动模式，避免原样抄写。

当前建议使用真实 Arduino C++ 的受限子集。可选择原生 API，或教学函数 readLight、setLamp、waitMs；教学函数必须有真实实现和手册说明，不能由模型每次临时翻译。最终 API 方案需在技术验证后冻结。

进入文本编辑前保存积木快照。返回积木时应提供“查看旧快照”或“复制成新分支”，不得静默覆盖新代码。不能映射回积木的语法给明确提示。

测试和编译通过后导出同一版本源码、引脚图和版本标识。网站显示“软件检查通过”，不能显示“实物已通过”。

## 6.6 S5 真机与教师验证

流程为断电接线 → 提交安全检查请求 → 教师现场确认 → 上电与烧录 → 学生自测 → 请求功能验收 → 老师批准或指出可修复原因。

默认使用预装 Arduino IDE/CLI 的限定电脑和板卡；浏览器一键烧录是单独技术验证项。无自动设备回读能力时，不把网页按钮点击视为真实烧录成功。教师机代为上传也必须使用该组确切源码版本，并记录实际操作方式。

教师验收记录包含小组、程序版本、接线版本、板卡型号、安全检查、亮暗行为、学生解释、结果和签核人。批准后的新修改产生新版本，需要复测；旧验收仍作为历史保留。

## 6.7 S6 商城和升级

先有基础交付，再开放进阶订单。商品只来自审核过、已具备接线资料和代码支持的模块目录。不能先把 OLED 或其他模块上架，再等学生买到后发现仿真、编译库或供电不支持。

工程币只在游戏内使用。基础材料免费，失败不扣主线资格。购买、扣币、库存与领件状态需分开记录；虚拟购买成功不代表真实零件已经领走。教师可关闭商城或替换缺货方案。

升级沿用“理解需求 → 改方案 → 测试 → 必要的实物安全复核与验收”。未做完可以保留探索记录，不把选修失败算作基础课程失败。

# 7 NPC 评审与 AI 服务

NPC 接收经过最小化处理的课程版本、当前阶段、需求卡、元件规格、接线与程序版本、测试记录和学生问题。它不能跨组读取，也不自动发送身份、学校和家庭信息。

评审输出建议为结构化对象：当前理解、引用的任务或测试证据、一个待回答问题、手册节号、建议下一步、是否需要教师协助。模型输出经过服务端校验后才能展示；不授予它奖励、验收和库存写权限。

评审状态使用待提交、讨论中、需要修改、已完成、教师协助完成。模型结论只是依据之一，通关策略由固定课程规则与已验证结果执行。AI 超时显示重试和静态问题卡，教师可以有记录地协助放行非安全教学节点。

提示层级依次为定位问题、引用资料、局部例子、教师救援。学生明确选择完整示例时可以提供受审核的基础方案，但记录使用支持，不给羞辱性标签。安全规则与教师通电检查不能被 AI 或“直接通关”提示绕过。

# 8 手册体系

网站负责当前委托、可操作工位和结果；手册负责可反复查阅的概念、规则、参数和排错依据。纸质与电子手册使用相同节号和版本，网站在卡点跳到相关节，而不是打开整本后让学生自己找。

建议学生工程手册结构：公司入职与工作流程、读懂需求、输入处理输出、开发板与 IO、标准元件资料、接线安全、积木语义、轻代码速查、测试与排错、实物上传、交付检查。教师参考答案和救援流程单独管理。

本轮开发文档定义手册接口和目录，不代替学生用的成品 Word 手册。纸质页码、完整示例和排版在板卡及语言方案冻结后制作，避免资料与实物不一致。

# 10 技术实现与一致性

推荐前端 TypeScript、Blockly 和代码编辑器，后端采用团队熟悉的框架。技术栈不是本轮强制决策；单一程序逻辑与版本追踪是硬要求。

程序链：积木生成受限 AST → 逻辑解释器执行测试 → 生成 Arduino C++；轻代码解析到同样的受限 AST → 使用同一语义和引脚映射 → 生成、编译、导出确切源码。禁止用模型临时把一份仿真程序改写成另一份实物程序。

C++ 子集需要正式解析和语义检查，不能用正则或提示词充当编译器。首期可限定编辑区域和模板，允许变量、比较、if/else、主循环、受支持的输入输出与等待；拒绝任意库、指针、动态内存、递归和系统调用。

仿真是逻辑与连接规则检查，不声称等价于完整电流、电压或噪声模拟。板卡、传感器读数方向、采样周期、延时和整数范围需有一致定义并做测试。示例阈值 450 不能未经实测直接用于所有光敏模块。

每个提交版本绑定需求、程序、接线、元件规格、手册和测试集版本。改变某项时仅使依赖它的后续通过凭证失效，不删除历史；本组仍可查看已交付的旧版本。

程序仿真设置执行步数和时间预算；编译在隔离环境运行并限制资源、源码大小和库访问。学生输入不得直接在业务进程 eval 或拼接系统命令。

# 11 数据与接口草案

新增或细化的实体：员工身份、班级场次、小组成员与编辑权、需求版本、阶段实例、程序版本、接线版本、测试运行、NPC 评审、硬件安全检查、实物验收、工程币账本、商城订单、领件记录、手册版本、个人反思和审计事件。

NPC 评审记录绑定 submission_id 和需求、代码、接线版本，保留引用证据与结论；不得只保存一段无法追溯的聊天。安全检查和功能验收是两个事件，避免在学生需要通电前已经被要求先证明功能正常。

建议接口分为加入场次、需求提交、评审会话、接线保存、程序保存、仿真测试、编译导出、安全检查申请、实物验收申请、教师签核、商城购买、领件确认和职业回顾。每个写接口必须校验角色、班级、小组、版本和幂等键。

主线状态：ENROLLED → REQUIREMENTS_READY → WIRING_READY → BLOCKS_PASSED → CODE_PASSED → HARDWARE_ACCEPTED → DELIVERED → REFLECTED。扩展订单另建分支，不回退基础交付。具体阶段统一使用 LOCKED、AVAILABLE、IN_PROGRESS、SUBMITTED、NEEDS_FIX、PASSED，并区分客观测试通过与教学协助完成。

重复提交不能重复奖励；买件和库存扣减同事务；验收需防跨组、过期和重复核销。刷新、弱网和多个教师同时处理不能产生矛盾状态。首期不做多人同步编辑器，采用编辑权租约及显式接管。

# 12 教学时间与课堂降级

四小时试排：入职 15 分钟、需求评审 20、硬件与接线 30、积木 Demo 40、休息 10、轻代码 35、实物 45、商城拓展 25、展示与回顾 20，共 240 分钟。这是试教起点，不是已验证时长。

快组可以提前进入拓展，慢组优先完成核心交付。教师验收按队列分批，不能要求全班同时等待一个长演示。班级人数、每组人数和师生配置继续以实际试教校准。

AI 不可用时用问题卡和审核手册；电脑无法烧录时换备用机或由教师上传同源代码；模块故障时替换标准件；网络中断时保留本地草稿、纸质任务和线下验收记录，恢复后由教师补录并审计。任何支持都不等于学生“作弊”，但报告应准确区分独立完成和协助完成。

# 13 开发拆分与交付门槛

| 阶段 | 交付 | 退出条件 |
| --- | --- | --- |
| M0 关键验证 | 固定板卡、元件、语言子集和烧录路径；跑通单一程序链 | 同一逻辑从积木、代码和虚拟测试到真实 LED，结果一致 |
| M1 一份订单纵向闭环 | 入职、需求卡、NPC、接线、积木、轻代码、教师验收的最简页面 | 一组用户无需开发者改数据完成主线 |
| M2 教学可用 | 手册节号、提示、自动保存、教师队列、弱网恢复和救援 | 零基础内部试玩可继续而不被系统锁死 |
| M3 游戏与拓展 | 工程币、审核商城、领件、成果板、扩展订单和报告 | 重复点击不重复扣发；选修不阻断结业 |
| M4 试教与正式验收 | 小规模真实学生试课、设备矩阵、隐私和许可检查 | 根据数据修订时间与难度，P0 缺陷关闭 |

不先做完整商城和复杂视觉再补编译链。最早可演示版本必须包含一份中文需求卡、一个 NPC 评审回合、一张接线图、一个积木程序、一次轻代码改动和一次真实硬件验收。

# 14 首发验收清单

- 新员工加入、刷新和换电脑后恢复正确小组与进度。

- 中文需求评审接受合理表达，不要求固定句子，不因模型超时永久卡关。

- 需求卡修改后生成新版本，NPC 不自动覆盖学生选择。

- 虚拟接线识别缺地、错误口、极性、缺电阻和电源短接。

- 接线中的端口与程序映射不一致时出现具体错误。

- 明暗及连续变化测试都验证实际程序输出，而非前端伪造通过。

- 修改阈值或代码后，旧测试不再作为当前版本通过证据。

- 文本编辑到积木切换不静默丢失改动。

- 仿真与生成源码在同一输入序列下具有一致的规定语义。

- 目标板卡和电脑能编译、上传并演示亮暗响应。

- 网页上传按钮或模拟通过不能冒充实物验收。

- 未经教师安全检查不能引导学生上电；未知模块要求人工确认。

- 教师只能批准本班组和指定版本，重复点击不重复发奖励。

- 多组同时申请检查和验收不丢请求，等待状态实时明确。

- 学生不能调用改币、签核或越权查询接口。

- 商城不超卖、不重复扣款，购买与实物领件分开。

- AI 不可用时仍有手册、问题卡和教师救援路径。

- 教师看得到阶段卡点，学生看不到他人私密记录。

- 排行榜不将 AI 的语言评价展示为职业或能力结论。

- 结束后交付摘要保留实际完成和未完成项，个人兴趣为自述。

- 真实零基础试教完成全链路；耗时和失败点用于修订，不虚报达成率。

# 15 开发前待确认事项

1. 轻代码采用 Arduino 原生 API，还是少量教学函数；是否允许学生写完整 loop。

2. 统一板卡批次、光敏模块型号和读数方向、LED 与限流方案。

3. 目标电脑、驱动和烧录方案；首期是否只承诺 IDE/CLI 路线。

4. 第一版基础测试阈值、循环与采样语义，哪些稳定性问题属于拓展。

5. 排行榜的展示对象、指标、名次及隐私范围。

6. 班级规模、每组人数、教师助教配置与验收排队安排。

7. 商城首期模块、虚拟库存与真实领料规则、退换机制及 EC 数值。

8. 公司与 NPC 的原创名称、手册风格和故事语气。

9. AI 服务商、预算、数据保存期限、未成年人相关授权与传输合规。

10. 实物功能验收能否记录版本证据，以及无自动设备回读时的教师确认方式。

上述事项按相关模块开工门槛处理。文档可支持原型与技术验证规划，但不把未冻结项当作生产发布承诺。
