## 客户测试与轨迹

每个 `CustomerTest` 保留五线草案中的 `id / requirementId / inputTimeline / assertions / maxSteps / maxTimeMs`，补充中文场景名、失败提示与手册节号。所属 suite 的 `requirementRef` 携带需求版本，不能只凭测试内的 `requirementId` 判断版本。

逻辑端口固定为 `light` 输入和 `lamp` 输出；前者是 0–1023 的合成整数且低值较暗，后者是布尔值且 `true` 为亮。由 E/B 显式映射到实际 profile 端口、端子和校准方向。D 未确认 Uno 代际、FQBN、供电、限流值或实物引脚。

需求 1.0.0：`light < 450` 时亮；需求 1.1.0：`light < 600` 时亮。两版均持续响应，输入变化后 200ms 内给出新状态；200ms 是本轮合成测试的候选时限，不是实测硬件指标。区间末尾再取样以检查状态保持。断言是手工冻结的字面量，不由学生参数计算，也不由 `runProgram` 的结果生成。

```js
// 最小可运行比较例：基础暗场景，灯保持为亮。
const sample = evaluateCustomerTrace({
  requirementVersion: '1.0.0',
  caseId: 'base-dark',
  simulation: {
    status: 'completed',
    simulatedUntilMs: 1200,
    events: [{ atMs: 0, outputs: { lamp: true } }],
  },
});
console.log(sample.passed); // true；仅一个场景，不能用它宣布整单通过。
```

用于实际集成的调用形态：

```js
// simulate 是 A 线的执行器，参数和 Result 包装由 E 适配。
const simulations = {};
for (const customerTest of getCustomerSuite('1.0.0').tests) {
  const run = simulate(program, topology, customerTest.inputTimeline, {
    maxSteps: customerTest.maxSteps,
    maxTimeMs: customerTest.maxTimeMs,
  });
  simulations[customerTest.id] = adaptSimulationResult(run);
}
const draft = evaluateCustomerSuite({ requirementVersion: '1.0.0', simulations });
const question = reviewStaticTechnical({ requirementVersion: '1.0.0', testRun: draft });
```

比较器需要的 `simulation` 形态：

```ts
type CustomerTrace = {
  status: 'completed' | 'budget_exceeded' | 'runtime_error';
  simulatedUntilMs: number; // 必须来自真实执行器的已推进时间
  totalSteps?: number;
  events: {
    atMs: number;
    step?: number;
    outputs: { lamp?: boolean }; // 明确输出或当时的输出快照
  }[];
};
```

`simulatedUntilMs` 是相对五线草案新增的候选覆盖字段：必须覆盖最后一条断言，且不超过场景的时间预算。不能由 E 在未执行的情况下直接补成 `maxTimeMs`，也不能把旧逐次计算结果标成真实时序。若 A 的实际字段名称不同，请由适配器读取等价事实。`content/demo.js` 故意只作合成输出比较，并明确不构成这项时序证据。

事件按毫秒非递减，同毫秒以最后一个写入为准；输出保持到后一次明确写入，缺失输出不自动解释为 `false`。布尔状态不接受 `0/1` 或字符串的隐式转换。解释器必须自己执行步数/时间限制；比较器只检查报告状态、轨迹结构及可选步数记录，不重新证明解释器的预算实现。每个场景独立重置程序状态。

返回值含 `authority:'local_draft'`、需求与测试集引用、每条断言的时间/预期/实际/通过结果、诊断与提示。固定 suite 的每个场景都必须有运行结果，缺一即失败。客户端提供的轨迹、`passed`、摘要或这些草稿结果都不能直接成为服务端通过凭证。E 须校验执行来源、个人权限、确切程序/接线/设备/手册/需求/测试版本并签发证据。

固定离散场景无法证明所有可能输入、短于采样间隔的瞬态或电路物理正确。尚未接入的 A 解释器时序、生成代码一致性和目标编译需要各自验证。

## NPC 与中文卡片

```js
const card = {
  input: 'light-sensor',
  condition: 'below-customer-threshold',
  output: 'dark-on-bright-off',
  continuous: 'repeat-read-decide',
  explanation: '我不断看光照，暗了亮、亮了灭，再变暗还能响应。',
};
const response = reviewStaticRequirements({
  requirementVersion: '1.0.0',
  card,
  fallbackReason: 'timeout',
});
```

可选项的中文标签与 ID 在 `npc.json.fields` 中。旧原型的中文值或任意真值不能隐式迁移成正确选项，E 应显式映射或提示重新选择。先保存草稿，提交时生成需求卡快照；静态服务不改写输入对象。

`requirement-card.schema.json`（也导出为 `requirementCardSchema`）定义已提交卡片的形状，枚举包括错误方案以支持真实评审。草稿可不完整；schema 不验证语义与通过状态。E 在快照层绑定个人、客户场景、需求版本与不做的功能，不接受卡片自报身份。此 schema 的版本对应订单的 `requirementSchemaRef`。

输出为 `mode:'static' / fallbackReason / questionId / question / citations / suggestedNextStep / needsTeacherHelp`，需求卡额外有 `coverage`。`coverage.readyForSubmission` 仅表示四项明确选项符合固定要求且有不超过 1500 字符的解释，始终伴随 `explanationReview:'semantic_review_pending'`。它**不是阶段通过或语义理解结论**，不能直接适配为旧 UI 的 `complete:true`。正确选项搭配错误解释的样例也保留待语义核对状态。

降级原因允许 `requested / offline / timeout / invalid_response / semantic_review_pending`。本模块不请求模型，不会产生 `mode:'ai'`。E 的线上 provider 校验或超时后可调用此入口；使用在线 AI 前仍需独立授权与数据规则。

引用 `path` 使用按 ID 定位的内容路径，例如 `sections/09.1`、`tests/base-dark`；这是逻辑定位符而非 JSON Pointer 的数组下标。需求路径如 `rule.whenFalse`。E/C 应用当前引用版本查找内容，不拼造纸质页码。

`reviewStaticTechnical` 接受当前 suite 的完整报告，遇到过期/不完整报告先要求重跑；失败报告指向第一个失败场景，预算错误指向循环与时间。`stage:'hardware'` 永远返回教师现场检查问题。问题卡不给阶段通过、奖励、库存或硬件批准字段。未来在线评审验收场景已列在 `review-examples.json`，本次只验证静态路径。

## 关卡、收入与商城

`stages.json` 的状态事件与 `passConditions` 是供 E 映射的规则标识，不是前端可写的状态机。编译缺失、实物未就绪应显示待验证；教师协助不能把未执行测试或硬件检查记成成功。`extension` 是独立选修，`reflection` 仅依赖基础 `delivery`。

已定“个人按收入排行”；候选默认是累计订单收入减明确撤销，购买仅扣余额，同收入同名次、稳定展示，默认不公开。默认候选基础交付 `300 EC`、升级 `100 EC`；按钮 `80 EC`、显示模块 `150 EC`，均为合成演示金额，未经确认。基础物料、求助和失败免费。没有入职赠币或按提问次数计奖。

E 负责账本实施，本模块只导出候选规则。重复结算除 `idempotencyKey` 外还须按“个人 + 订单”约束，防止换键或换提交版本重发；购买和退款不改变累计收入；撤销另建事件。物品目前全部 `blocked_pending_validation`、实物库存 `null`，不能视为可售品或已采购。正式上架需模型、资料、语言、编译和实物验证证据齐备。

## 游戏体验增量候选

`firstOrderExperienceCandidate`（原始 `auto-lamp/experience.candidate.json`）定义一个当前目标、三处可跳过探索、两张元件用途卡、事件对应反馈与工作档案候选。E 已约定的纯导航动作 ID 为 `open_mail / talk_requirements_npc / inspect_kit / open_manual`，`onAction` 的实际调用形态仍由 E 拥有。旧讨论 ID 仅作 alias，不另建第二套公共协议。

当前目标与反馈显示从 E 的个人快照/事件派生；点击或已访问计数不能改变通过、保存、运行、收入、库存或教师状态。场景与普通文字列表提供等价路线，探索不必全做。金额继续来自 E 的 synthetic 账本，未在本候选中写死。此次导出是增量数据，不能将它当成已实现的新场景或已验证教学效果；见同目录游戏性审查和截图范围说明。
